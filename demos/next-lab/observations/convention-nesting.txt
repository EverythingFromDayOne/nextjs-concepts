`error.tsx` and `not-found.tsx` never appear in a successful render — they
are boundaries/fallbacks that only materialize when something actually
throws or calls `notFound()`. Their *position* in the wrapper stack, read
from the RSC payload's `error`/`template` props on the internal layout
router component (and confirmed by experiment C and the antipattern check),
is: error.tsx wraps `loading.tsx`, `not-found.tsx`, `page.tsx`, and any
nested `layout.tsx` — but it sits **inside** both `layout.tsx` and
`template.tsx` in its own segment, never wrapping either. So the full nest,
outside to inside, is: `layout` → `template` → (invisible error boundary) →
`loading`'s Suspense → `page`/`not-found`.

**Correction to the prompt's premise, stated plainly:** the bundled
`next@16.3.0` docs (`01-app/01-getting-started/02-project-structure.md`,
"Component hierarchy") already publish this exact order as text, not just
an image — `layout.js`, `template.js`, `error.js` (error boundary),
`loading.js` (Suspense boundary), `not-found.js` (error boundary), then
`page.js` or nested `layout.js` — and states plainly that each is nested
**inside** the previous. The rendered measurement above **confirms this
documented order rather than contradicting it**: this article's own
"one connected wrapper stack" framing lines up with what next@16.3.0
actually ships. What the doc's bullet list doesn't make obvious — and what
required rendering to see — is *which of the six are real, always-present
DOM wrappers versus invisible/conditional boundaries*: only `layout` and
`template` emit a DOM node unconditionally. `loading` never emits a DOM
node of its own either — it's the `fallback` prop of one Suspense boundary
sitting inside `template`'s `children` slot, visible only while that
boundary is pending. `error` and `not-found` are boundary components with
zero rendered output in the successful path — they materialize only when
something throws or `notFound()` is called, and even then only one of the
two (plus `page`) can be showing at a time, because they're alternate
outcomes of the same position in the tree, not stacked siblings. So the
measured nest is real, and matches the docs — but "nested inside" reads
differently once you know three of those six names are conditional
fallbacks for the same slot rather than six DOM layers.

## 2. /conventions/nested — inheritance

  data-marker="layout"        (inherited from /conventions/layout.tsx)
  data-marker="template"      (inherited from /conventions/template.tsx —
                                YES, template.tsx applies to a child segment
                                with no template.tsx of its own)
  data-marker="nested-page"   (this segment's own page.tsx)

No `data-marker="loading"` appears for `/conventions/nested` — not because
loading.tsx failed to inherit, but because the inherited Suspense boundary
resolved *before* it ever needed to show its fallback: `nested/page.tsx`
has no dynamic API and nothing to defer, so the boundary from
`/conventions/loading.tsx` completes synchronously. Confirmed by reading
`.next/server/app/conventions/nested.html`: the boundary marker at that
position is `<!--$-->` (already-resolved Suspense), not `<!--$?-->`
(pending/showing-fallback) — the same marker `/conventions` itself gets
once its own page resolves. The mechanism is present and inherited either
way; only whether it's ever *visibly* exercised depends on the leaf page.

## 3. Shell membership — .next/server/app/conventions.html

Present in the shell (stripped to data-marker elements, in nesting order):

  data-marker="layout"
  data-marker="template"
  data-marker="loading"

Absent from the shell: `data-marker="page"`.

**Confirmed as predicted.** The raw shell HTML contains
`<div data-marker="template">...<!--$?--><template id="B:0"></template>
<p data-marker="loading">loading</p><!--/$--></div>` — `<!--$?-->` is
React's pending-Suspense marker, meaning the shell captured the *fallback*,
not the page. `page.tsx` calls `connection()`, which defers its subtree past
the point where static generation can include it, so the compiled static
shell for `/conventions` stops at layout → template → loading's fallback.

For contrast, `.next/server/app/conventions/nested.html` shows `<!--$-->`
(resolved, not pending) at the equivalent position, because `nested/page.tsx`
has no dynamic API — its shell **does** include the page content, wrapped in
layout and template, with no loading fallback baked in (nothing to fall back
from).
