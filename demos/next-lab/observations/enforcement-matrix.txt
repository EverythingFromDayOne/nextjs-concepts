### Probe 9 follow-up: does the message change if the prop isn't named like a DOM event handler?
Probe 9 above used a prop literally named `onClick`, which React/Next special-case: any
prop matching the `on*` event-handler naming convention gets the more specific
"Event handlers cannot be passed to Client Component props." error before the generic
function-serialization check ever runs. Re-ran with the same function passed under a

### Probe 8 follow-up: the "Server Component imported into a Client Component" claim is more nuanced than a single verdict
The original probe 8 (async component doing an uncached `db` call, imported into a Client
Component) failed at build � but the error it hit (`blocking-prerender-dynamic`, "Next.js
encountered uncached or runtime data during prerendering") is the **same generic error any
uncached-fetch-outside-Suspense route gets**, unrelated to crossing the client boundary. That
result alone doesn't establish that importing a Server Component into a Client Component is
itself rejected. Ran two more variants to isolate the actual rule:

**8b � a component with no directive and no server-only API, pure sync JSX, imported into a
Client Component:**
```
app/scratch-s7-p8b/server-part-sync.tsx (no directive):
  export default function ServerPartSync() {
    return <p>plain sync component, no directive, no server-only import</p>
  }
app/scratch-s7-p8b/client-wrapper-sync.tsx:
  'use client'
  import ServerPartSync from './server-part-sync'
  export default function ClientWrapperSync() {
    return <div><ServerPartSync /></div>
  }
```
build: **PASS** (exit 0) � route shipped as `? /scratch-s7-p8b` (fully static).
Rendered HTML contains the component's output: `plain sync component, no directive, no server-only import`.
`page_client-reference-manifest.js` lists only `client-wrapper-sync.tsx` as a client module �
`server-part-sync.tsx` is **not** a separate entry; its code was silently inlined into the
client bundle. **Nothing failed. Nothing warned.** A component with no server-only content is
not "a Server Component" in any way the compiler can detect or enforce once it's reached from
a Client Component's import graph � it's just a function, and it runs wherever its importer runs.

**8c � a component using a genuinely server-only Node API (`next/headers`), imported into a
Client Component:**
```
app/scratch-s7-p8c/server-part-headers.tsx (no directive):
  import { headers } from 'next/headers'
  export default async function ServerPartHeaders() {
    const h = await headers()
    return <p>{h.get('user-agent')}</p>
  }
app/scratch-s7-p8c/client-wrapper-headers.tsx:
  'use client'
  import ServerPartHeaders from './server-part-headers'
  export default function ClientWrapperHeaders() {
    return <div><ServerPartHeaders /></div>
  }
```
build: FAIL (exit 1)
build error (first line): Error: Turbopack build failed with 1 error:
full extract:
```

Import traces:
  Client Component Browser:
    ./demos/next-lab/app/scratch-s7-p8c/server-part-headers.tsx [Client Component Browser]
    ./demos/next-lab/app/scratch-s7-p8c/client-wrapper-headers.tsx [Client Component Browser]
```

**CONTRADICTS THE ARTICLE'S FRAMING.** `foundations/server-and-client-components` and this
article's own "four scopes" table both state flatly that a Server Component "may not be
imported by a Client Component." That's not what's enforced. What actually happens: importing
a directive-less module from a Client Component **silently reclassifies that module as a
Client Component too** (see 8b � no error, no warning, it just runs on the client from then
on). The build only fails if that now-reclassified module then uses an API the client bundle
genuinely cannot satisfy (`next/headers`, `next/cookies`, `fs`, etc. � 8c), or if it does
uncached-and-unsuspended data access, which fails for the ordinary blocking-prerender reason
(the original probe 8) and would fail identically outside a Client Component too. There is no
enforcement point that says "a Server Component may not be imported into a Client Component" �
there is only "a module that ends up in the client bundle may not use server-only APIs," which
is the same rule that already governs every other client-bundle import. Both existing
articles' phrasing should be corrected to describe reclassification, not rejection.
